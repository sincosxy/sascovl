# CargoFlow

Личный кабинет заказчика и рабочее место оператора для каботажной контейнерной линии
(Владивосток ↔ Корсаков / Магадан / Петропавловск-Камчатский).

Клиент оформляет заявку на перевозку пошаговым мастером. Оператор утверждает заявку,
назначает номера контейнеров и PIN-коды, заводит рейсы, ставит контейнеры в рейсы и
присваивает номера коносаментов. Клиент видит статус, рейс и коносамент и получает уведомления.

> Этот файл описывает текущее состояние проекта. Подсказки и ловушки для ИИ-ассистента —
> в [`context.md`](context.md). История изменений — в `git log`.

## Стек

| Слой | Технологии |
|---|---|
| Backend | Python 3.10 (в Docker), FastAPI, SQLAlchemy 2 (async, `asyncpg`), Alembic |
| Frontend | Jinja2 + HTMX 2 + Alpine.js + Tailwind (CDN), без сборки |
| БД | PostgreSQL 15 |
| PDF | `xhtml2pdf` (Booking Note) |
| Внешние API | DaData (подсказки адресов и компаний), FESCO (расписание), ВМТП (требования таможни) |

Интерфейс — одна страница: HTMX подменяет содержимое `<main id="main-content">` HTML-фрагментами с сервера.

## Роли

| Роль | Что может |
|---|---|
| `USER` (клиент) | Свои заявки: создать, править черновик, подтвердить, отменить; свои контрагенты; уведомления |
| `OPERATOR` | Все заявки, контейнеры, рейсы, коносаменты, компании, проверка требований ВМТП |
| `ADMIN` | Всё, что оператор, плюс управление пользователями |

Регистрации нет: пользователей создаёт администратор.

## Модель данных

- **User** — `email`, `role`, `is_active`, `company_id`.
- **Company** — реквизиты компании клиента (мягкое удаление `is_deleted`).
- **Counterparty** — отправители/получатели/перевозчики; у каждого пользователя свой список.
- **Port**, **Equipment** (20DC, 40HC…), **Vessel** — справочники.
- **CargoOrder** — заявка: владелец, маршрут (`pol_id` → `pod_id`), стороны (`shipper`, `consignee`,
  `notify_party`), наземная доставка, `status`, `is_valid`.
- **Container** — контейнер заявки: номер, `valid_number`, пломба, PIN, вес, реф-параметры,
  отмена (`is_cancelled` + причина), **`arrived_at`** (дата поступления на терминал, кто подтвердил —
  `arrival_confirmed_by_id`), **`voyage_id`** и **`bl_number`** (рейс и коносамент).
- **CargoItem** — грузовые позиции внутри контейнера (LCL).
- **Voyage** — рейс: номер, судно, порты отправления/назначения, даты.
- **Notification** — уведомление пользователю (`text`, `order_id`, `is_read`).
- **ContainerArchive**, **ProcessedFile** — архив упоминаний контейнеров в PDF терминала (для проверки требований).

### Статусы заявки (`CargoOrder.status`)

| В базе | На экране | Когда |
|---|---|---|
| `draft` | Черновик | Клиент заполняет мастер. Только в этом статусе клиент может править заявку |
| `CONFIRMED` | Подтверждён / Новая заявка | Клиент отправил заявку. У оператора — блок «Новые заявки — ждут обработки» |
| `IN_PROGRESS` | В работе | Оператор нажал «Подтвердить и запустить» |
| `EXECUTING` | Выполняется | Все неотменённые контейнеры заявки стоят в рейсах |

`IN_PROGRESS` ↔ `EXECUTING` переключается автоматически (`bl.sync_order_status`) при постановке
в рейс, снятии с рейса, отмене/восстановлении контейнера, удалении рейса, утверждении заявки.

`is_valid = False` — заявка отменена клиентом («мягкое» удаление): у клиента пропадает из списка,
у оператора остаётся с пометкой «Отменён клиентом». Физически удалить заявку может только
оператор/админ (`DELETE /admin/orders/{id}`).

## Основные сценарии

**Клиент.** `POST /api/orders/init` создаёт черновик → шаги `step-1` (маршрут, оборудование, SOC/COC) →
`step-2` (контейнеры и грузы) → `step-3` (стороны и автодоставка) → `step-4` (сводка) → `confirm`.
Список заявок — `GET /api/orders`, детали — `/details` (раскрывающийся блок) и `/summary` («Просмотр»),
PDF — `/pdf`. Отмена — `POST /api/orders/{id}/cancel`.

**Оператор.** Дашборд `/admin/dashboard` → «Обработать» (`/api/operator/orders/{id}/manage`): номера
контейнеров, PIN-коды, отмена контейнеров, утверждение. Рейсы — `/voyages/`, контейнеры — `/containers/`.

**Поступление на терминал.**
- Клиент вводит пломбу в раскрывающемся блоке заявки (сохраняется при уходе с поля). Все активные
  операторы и админы получают уведомление (непрочитанное уведомление о том же контейнере заменяется).
  Если пломбы указаны ещё в мастере — одно уведомление при подтверждении заявки.
- Оператор подтверждает поступление с датой (по умолчанию сегодня по Владивостоку, будущая дата
  запрещена): на странице «Обработать» заявки, в строке списка контейнеров или группой
  (`/containers/?view=arrival` — «Ждут приёма»). Без пломбы и в черновике подтвердить нельзя.
  Клиент получает уведомление. Отметку можно отменить, пока контейнер не в рейсе.
- После подтверждения клиент пломбу больше не меняет (её правит оператор в карточке контейнера).

**Контейнеры в рейсах.**
- Страница рейса `/voyages/{id}/containers`: что уже в рейсе (с коносаментами) и свободные контейнеры
  с чекбоксами; групповая постановка и снятие; ручная правка номера коносамента.
- Список `/containers/?view=active|planned|cancelled|all`: «Активные» — ещё не в рейсе; панель
  группового переноса выбранных контейнеров в рейс.
- В рейс ставится только неотменённый контейнер **с номером, пломбой и подтверждённым поступлением
  на терминал** из подтверждённой
  (не черновик, не отменённой) заявки. Несовпадение маршрута заявки и рейса — предупреждение, не запрет.

### Номер коносамента

Формат: `Кор0123V001K`

| Часть | Значение |
|---|---|
| `Кор` | Линия: `Кор` / `Маг` / `Пет` — по порту рейса, который не Владивосток (если оба линейные — по порту назначения) |
| `0123` | Последние 4 цифры номера рейса, с нулями слева |
| `V` | Первая буква порта отправления: `V`, `K`, `M`, `P` |
| `001` | Порядковый номер коносамента в рейсе (максимальный выданный + 1) |
| `K` | Первая буква порта назначения |

Порты распознаются по названию (Владивосток, Корсаков, Магадан, Петропавловск). Если порт рейса
не из этого списка, контейнер ставится в рейс без номера, номер вводится вручную.
Режимы выдачи: отдельный коносамент на каждый контейнер (по умолчанию) или один на заявку.
Вся логика — в `app/bl.py`.

### Уведомления

Колокольчик в шапке клиентского кабинета (`base.html`) и оператора (`operator/base_ops.html`),
счётчик опрашивается раз в минуту.
Клиенту — при утверждении заявки оператором, приёме контейнера на терминал (и отмене отметки),
постановке контейнера в рейс (с номером коносамента), снятии с рейса.
Операторам и админам — когда клиент указал пломбу или подтвердил заявку с пломбами.
Только внутри кабинета — без почты и мессенджеров.

## Запуск локально

Нужен файл `.env` в корне (в git не попадает):

```
POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB
PGADMIN_DEFAULT_EMAIL, PGADMIN_DEFAULT_PASSWORD   # обязательны для старта приложения
SECRET_KEY, ALGORITHM, ACCESS_TOKEN_EXPIRE_MINUTES
DADA, FIT, VMTP_USER, VMTP_PASSWORD               # токены внешних API
```

```bash
docker compose up -d                    # только PostgreSQL
docker compose --profile tools up -d    # PostgreSQL + pgAdmin (http://127.0.0.1:5051)
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
python create_first_admin.py            # первый админ: логин/пароль из PGADMIN_DEFAULT_*
uvicorn app.main:app --reload
```

`docker-compose.override.yml` (в git не попадает) публикует порт 5432 для локальной разработки.

## Деплой

На сервере приложение работает в Docker с профилем `prod`; pgAdmin там не поднимается (профиль `tools`).

```bash
./deploy.sh             # git pull, пересборка образа только при смене зависимостей, перезапуск
./deploy.sh --migrate   # то же + alembic upgrade head
./deploy.sh --build     # принудительная пересборка образа
```

Код смонтирован в контейнер томом, поэтому правки Python и шаблонов не требуют пересборки.
После изменений в `models.py` всегда нужна миграция: приложение при старте делает `create_all`,
но он создаёт только новые таблицы и **не добавляет колонки** в существующие.

Текущая голова миграций: `f3a9c2d4e5b1`.

## Безопасность — что сделано и что нет

Сделано: проверка владельца на всех клиентских эндпоинтах заявок, правка заявки только в статусе
черновика, cookie сессии `HttpOnly` + `SameSite=Lax` + `Secure` при HTTPS, `.env` не попадает в образ.

Известные незакрытые вопросы (подробнее в `context.md`): нет ограничения попыток входа, токен
не отзывается при выходе, `/docs` открыт, XSS в местах, где HTML собирается f-строками,
оператор может править и удалять компании.
